# 0032 — Mises à jour des applications installées depuis l'application

**Statut** : Décidé (11 novembre 2026), mis en œuvre en 1.17.0

## Contexte

Les applications Windows et Android (décision 0020) se mettent à jour à la main : la bannière « Nouvelle version de l'application » ouvre la page Applications, qui ouvre le fichier sur GitHub dans le navigateur ; il faut ensuite installer l'APK par-dessus, ou décompresser le zip à la place de l'ancien dossier. La feuille de route de la phase 6 prévoit l'**installation automatique des mises à jour des applications**.

Contraintes : aucun appel réseau sortant non demandé par l'utilisateur ; aucune télémétrie ; Android n'installe jamais une application sans confirmation de l'utilisateur (hors appareils gérés) ; les fichiers ne sont pas signés par un éditeur sous Windows (décision 0021 : sommes SHA-256 et signatures Sigstore publiées avec chaque version) ; la clé de l'APK est fixe depuis la 1.1.1.

## Décision

1. **Un geste, jamais à l'insu de l'utilisateur.** Dans les applications connectées à un serveur, la bannière propose **« Installer »** quand le serveur est plus récent, et la page Applications **« Installer la version X »**. La version visée est celle du serveur (jamais au-delà, l'application et le serveur restant accordés). En mode autonome (décision 0022), il n'y a pas de serveur pour le dire : la page Applications propose **« Rechercher une nouvelle version »**, qui demande à GitHub l'adresse de la dernière version publiée (`releases/latest`, sans suivre la redirection, rien d'autre n'est envoyé). Rien n'est vérifié ni téléchargé tout seul.
2. **Source et vérification.** Le fichier de la plateforme (`owncoffer-X.Y.Z-android.apk` ou `owncoffer-X.Y.Z-windows-x64.zip`) et `SHA256SUMS` sont téléchargés depuis la version GitHub correspondante, en HTTPS. Le fichier est écrit dans le cache de l'application, limité à 300 Mo, puis sa somme SHA-256 comparée à celle publiée ; s'il ne correspond pas ou que la somme manque, il est effacé et l'installation refusée.
3. **Android.** Avant de lancer l'installateur du système, l'application vérifie dans l'APK téléchargé le nom du paquet (`org.owncoffer.app`), la version attendue et que **son certificat de signature est celui de l'application installée** ; sinon elle refuse avec un message clair (au lieu du « conflit avec un paquet existant » d'Android). Elle ouvre ensuite l'installateur d'Android, qui demande la confirmation ; la première fois, Android demande aussi d'autoriser OwnCoffer à installer des applications (permission `REQUEST_INSTALL_PACKAGES`, page des réglages ouverte, puis « Réessayez »). Le fichier est partagé avec l'installateur par un `FileProvider` limité au dossier `updates/` du cache.
4. **Windows.** L'archive vérifiée est décompressée (`Expand-Archive`) dans un dossier voisin de celui de l'application (`<dossier>.update`), dont on vérifie qu'il contient `owncoffer.exe`. **Le dossier de l'application doit ne contenir que des fichiers de la version** (mêmes noms que dans l'archive) : s'il contient autre chose (application décompressée dans Téléchargements ou sur le bureau), la mise à jour est refusée, pour que rien de l'utilisateur ne soit jamais déplacé ni effacé. Après confirmation (« Fermer et mettre à jour »), l'application écrit un petit script `cmd` dans le dossier temporaire, le lance et se ferme ; le script attend la fin du processus, renomme l'ancien dossier en `<dossier>.previous`, met le nouveau à sa place et relance OwnCoffer. Si un renommage échoue (dossier protégé, fichier ouvert), l'ancien dossier est remis en place et la nouvelle version lancée depuis `<dossier>.update`. Au lancement suivant, l'application efface les téléchargements du cache et `<dossier>.previous` (seulement s'il contient `owncoffer.exe`). Un chemin contenant `%` ou `"` est refusé (mise à jour à la main).
5. **Données gardées.** Les données ne sont pas dans le dossier de l'application : session et réglages dans le coffre de l'appareil, base du mode autonome dans le dossier de données de l'utilisateur. Le mode autonome met sa base à jour au démarrage, comme lors d'une mise à jour à la main ; une sauvegarde d'une version plus ancienne reste lisible (décision 0022).
6. **Échecs affichés, toujours une sortie.** Réseau, somme fausse, fichier trop gros, autorisation Android, signature différente, dossier impossible à préparer : chaque cas a son message, avec « Télécharger à la main » qui ouvre le fichier comme avant.
7. **Pas sur le web** : la version web est servie par le serveur, toujours à sa version.

## Conséquences

- Plus besoin de passer par le navigateur pour mettre à jour ; Android garde sa confirmation, Windows redémarre tout seul.
- La somme SHA-256 vient de la même version GitHub que le fichier : elle protège d'un fichier abîmé ou tronqué, pas d'un dépôt compromis. Sous Android, la vérification du certificat de signature couvre ce cas ; sous Windows, la vérification Sigstore et un certificat d'éditeur restent à faire (feuille de route : « certificat de signature Windows »).
- Une installation dans un dossier protégé (par exemple `Program Files`) ne peut pas être remplacée : la nouvelle version tourne depuis le dossier voisin, ou se met à jour à la main.
- Le code natif est compilé et testé par la CI (APK et Windows) ; la logique (sommes, version la plus récente, script) est testée en Dart.
